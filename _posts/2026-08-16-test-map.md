# 테스트 지도

최종 수정 2026-08-22 11:34 KST

**이 프로젝트의 테스트는 두 종류다.** 이름도 실행법도 판정 방식도 다르고, 서로를 대신하지 못한다.

||**pytest**|**harness**|
|---|---|---|
|어디|`tests/` — 66개 파일|`eval/harness.py` + `eval/corpus.md`|
|규모|1,123개 테스트|질의 125개|
|**묻는 것**|LLM이 나쁜 SQL을 만들어도 **사용자에게 안 닿나?** 우리 숫자가 맞나?|LLM이 **좋은 SQL을 만드나?**|
|LLM 호출|**없음** (전부 모킹·픽스처)|**있음** — 질의마다 실제 콜|
|검사 대상 SQL|테스트 파일에 **손으로 박아둔 픽스처**|LLM이 **방금 생성한 것**|
|판정|통과 / 실패 (결정론적)|PASS / FLAG / ERROR (**확률적**)|
|소요·비용|수십 초, 무료|전량 1롤 ~9분, **실제 비용 발생**|
|언제|**소스를 고칠 때마다**|프롬프트·모델을 바꿀 때, 배포 전|
|실행|`uv run pytest`|`uv run python eval/harness.py --escalate 3`|

**왜 둘 다 필요한가.** pytest는 우리 코드가 맞는지 결정론적으로 증명하지만, LLM이 오늘 실제로 무엇을 생성하는지는 모른다. harness는 그것을 실측하지만 비결정적이라 무엇도 증명하지 못한다 — 1롤은 증거가 아니다. 그래서 **harness가 발견하고 pytest가 잠근다**: 하네스 스윕에서 결함이 나오면 그 모양을 손으로 재현한 픽스처가 `tests/`에 들어가고, 그때부터 그 결함은 공짜로 영원히 막힌다. 린트 10종이 전부 이 경로로 생겼다.

pytest가 LLM을 안 부르는데도 "나쁜 SQL"을 검사할 수 있는 이유도 거기 있다. **LLM이 할 일(결함 있는 SQL 만들기)을 테스트 작성자가 대신한다.**

파이프라인이 _어떻게_ 도는지는 `SQL_VALIDATION_PIPELINE.md`에 있다. 이 문서는 그 파이프라인과 앱 전체를 _무엇이 지키고 있는지_를 두 종류 모두에 대해 정리한다.

## 층 관계 — 무엇이 무엇의 잣대인가

5번과 4번은 **순서가 있다.** pytest는 1,021개를 한 번에 돌리므로 실행 순서 강제는 없지만, 논리적으로 5번이 무너지면 4번이 초록이어도 의미가 없다 — 잣대가 틀렸는데 잣대와 맞는지만 본 셈이 된다.

```
[6번 린트 72개]  SQL 텍스트만 보고 판정 (실행 전)
       │
[5번 스탯 정확성 74개]  canonical SQL·매크로가 맞나?
   앵커(외부 KBO 기록) · 불변식(데이터 자체 논리) · pandas 독립재구현 · 골든스냅샷
       │  통과하면 잣대로 신뢰
       ▼
[4번 차등 가드 123개]  그 잣대로, 결함 SQL이 걸리나?
   픽스처 SQL 실행 → 기준과 값 대조 → re-roll/거부
```

잣대(값 B)의 소재는 스탯 종류마다 다르다. 자세히는 SQL_VALIDATION_PIPELINE.md의 「공식은 어디 사는가 — 생성 층과 검증 층」 절.

|스탯|잣대|파일|
|---|---|---|
|OPS+ / ERA+|canonical SQL 6종 (통산·시즌별·**팀시즌** × 2스탯)|`canonical_sql.py`|
|OPS/OBP/SLG/AVG/ERA/WHIP/ISO/BABIP|카운팅에서 재조립한 인라인 식|`queries.py` `_CANON_RATE`|
|HR/H/G/W/SV…|그 선수(또는 그 리그·팀 그룹)의 전 행 SUM, **많을 때만**|`queries.py` `_COUNT_TABLES`|

# Part 2 — harness

`eval/harness.py` (727줄) + `eval/corpus.md` (질의 124개). **실제 LLM을 부른다.**

코퍼스의 질문마다 SQL을 생성하고, 실행하고, **정답 없이(reference-free)** 결과가 수상한지 판정한다. 핵심은 사람이 손으로 부딪혀 발견하기를 기다리지 않고 **자동으로 의심스러운 리더보드를 드러내는 것**이다.

## 프로덕션 경로를 그대로 탄다

하네스는 LLM 응답을 바로 채점하지 않는다. `_production_generate`가 `app._cached_generate`의 본문을 그대로 미러링한다 (Streamlit 캐시만 뺀다) — 생성 → `validate_sql` → repair → `_reroll_if_wrong`.

**그래서 앱이 조용히 고쳐냈을 일시적 나쁜 SQL은 실패로 세지 않는다.** 실제로 사용자에게 도달하는 것만 센다. 이게 하네스 수치를 "모델의 원본 정확도"가 아니라 **"파이프라인 통과 후 정확도"**로 읽어야 하는 이유다.

한 가지 예외를 둔다: 거부는 `LLMResponse(error=...)`를 SQL 없이 반환하므로(못 쓰는 SQL이 캐시되거나 서빙되지 않게 하는 의도된 설계), 하네스는 **repair에 넘기기 전에 원본 SQL을 붙잡아 둔다.** 그러지 않으면 `flagged.jsonl`에 `sql: null` 레코드만 남아 근본원인 추적이 `app.log`를 타임스탬프로 뒤지는 일이 된다.

## 실행

```bash
uv run python eval/harness.py                  # 전량 1롤 (124개, ~9분)
uv run python eval/harness.py "질문"            # 단일 임의 질의
uv run python eval/harness.py --repeat 3       # 전부 3롤 — 질의별 통과율
uv run python eval/harness.py --escalate 3     # 1롤씩, 위험한 것만 3롤
```

**`--repeat`가 존재하는 이유는 생성이 비결정적이기 때문이다.** 5롤 중 1롤에서 나오는 버그는 단일 롤 실행이 ~80% 놓친다(실측 — PA 가중 통산 OPS가 한 번 나왔다가 다음 실행에 사라졌다). 비용이 롤 수에 정비례하므로 **롤 수는 항상 미리 승인받고 쓴다.**

**`--escalate`는 예산을 위험한 곳에만 쓰는 싼 변형이다.** 실패 이력이 없는 질의는 1롤, `flagged.jsonl` (실행을 넘어 누적된다)에 이력이 있는 질의는 처음부터 full budget, 그리고 **이번 실행에서 실패한 질의는 그 자리에서 증량**한다 — 갓 생긴 간헐 결함도 재현율이 측정된다. 깨끗한 코퍼스에서는 사실상 1롤씩이라 N=3 기준 348콜이 아니라 124콜이다.

## 판정 — PASS / FLAG / ERROR

|판정|뜻|심각도|
|---|---|---|
|**FLAG**|검출기가 값을 수상하다고 지적 — **틀린 차트가 그려졌다**|가장 나쁨|
|**ERROR**|가드가 거부했다 — 방문자는 답을 못 받았지만 **틀린 답을 받지도 않았다**|중간|
|**PASS**|검출기 전부 침묵||

여러 롤을 돌리면 대표 판정은 **가장 나쁜 롤**이다 (FLAG > ERROR > PASS). FLAG가 ERROR보다 나쁜 이유가 이 순서에 들어 있다 — 거부는 정직하지만 그려진 오답은 그렇지 않다.

그리고 **롤마다 판정이 달라진 질의는 `불안정`으로 따로 나열된다.** 그 목록이 곧 간헐 결함 신호다. `Id`가 없어 필터 검증이 불가능했던 질의도 별도로 출력한다 — 맹점을 숨기지 않고 보이게 하려는 것이다.

### 검출기가 결과에서 Id를 찾아내는 방법

여러 검출기가 `Id`를 필요로 하는데, 결과에 Id 컬럼이 없어 보이는 경우가 많았다. 두 우회로가 커버리지를 크게 올렸다 — **프롬프트를 하나도 안 고치고**:

- `_result_ids` — 프롬프트 규칙 9가 동명이인 구분을 위해 `양준혁 #93410` 형태의 `player_label`을 SELECT한다. Id가 결과에 내내 있었는데 아무도 안 보고 있었다. 필터 검증 커버리지 **16개 중 8 → 13**.
- `_pinned_ids` — 단일 선수 추이 SQL은 Id가 아니라 **이름으로** 필터한다(`WHERE Player = '이승엽'`). 이름을 데이터로 해소하면 Id가 나오고, 동명이인이면 여러 개가 나와 검사가 스스로 물러선다.

## `eval/corpus.md` — 무엇을 넣고 무엇을 안 넣나

질의 124개. 한 줄에 하나, `#`로 시작하면 주석. 형식은 `tests/test_corpus_format.py`가 지킨다 — 들여쓴 주석 한 줄이 **실제 LLM 콜을 조용히 써버리기** 때문이다.

두 가지 설계 규칙이 명시돼 있다:

- **rate 스탯 위주로 의도적으로 편향.** 단순 카운팅 리더보드(`통산 홈런 탑10`)는 사실상 안 틀리고, 버그는 rate에 산다. 앱이 지원하는 rate 전부를 훑되(OPS, OPS+, SLG, OBP, ERA, ERA+, ISO, K%, BB%, K/BB, HR%, WHIP, FIP) 차등이 독립 재계산할 수 있는 평범한 통산 리더보드 모양을 선호한다.
- **패밀리당 한 항목.** 상수만 다른 질의(`탑 10` vs `탑 20`, `최소 800이닝` vs `1000이닝`)는 같은 테스트다 — SQL 모양이 같고 콜만 하나 더 쓴다. **차트 방향도 이유가 안 된다**: 가로 전환은 LLM을 거치지 않는 렌더 층 규칙이고 임계 양쪽이 이미 `tests/test_bar_orientation_sort.py`에 잠겨 있으며, 애초에 하네스는 차트를 그리지 않는다. **SQL이나 노출되는 행이 달라질 때만** 변종을 남긴다.

질의는 전부 실사용에서 나왔다 — 예시 버튼(`user_prompt_examples.md`), 블로그의 프롬프트 목록, 그리고 28일치 실제 `app.log`.

## `eval/flagged.jsonl` — 실행을 넘어 누적되는 증거

FLAG/ERROR가 난 실행마다 `{ts, query, status, reasons, sql, rows}`를 append한다. 생성이 비결정적이라 **문제의 SQL을 붙잡을 수 있는 단 한 순간이 flag되는 그때**이기 때문이다.

이 파일은 두 가지 역할을 한다:

1. **근본원인 추적** — 간헐 결함의 실제 SQL이 남는다
2. **`--escalate`의 입력** — 실패 이력이 있는 질의를 판별하는 기준

현재 27개 레코드(FLAG 14 / ERROR 13), 고유 질의 11개. 이력이 쌓일수록 `--escalate`가 비싸지므로 날짜 창으로 감쇠시킬 계획이고, 고유 질의 50건 근처가 착수 시점이다.

# 두 종류는 어디서 만나나

pytest와 harness는 **같은 코드를 공유한다.** 이것이 사고로 그렇게 된 게 아니라, 갈라졌던 것을 합친 결과다.

## 공유 단일 소스

|공유물|어디|왜|
|---|---|---|
|`_differential_flags`|`queries.py`|네 벌의 복제본이 **이미 드리프트해 있었다** — +stat 허용오차가 프로덕션 0.5 / 하네스 하드코딩 0.15로 갈라져 있었고, 하네스의 통산 버전만 `with_player_label_id` 복구가 빠져서 라벨 붙은 리더보드가 프로덕션에선 검사되고 오프라인에선 **조용히 건너뛰어졌다**. 이제 차이는 전부 인자라 명시하지 않으면 존재할 수 없다|
|`checkable_season_ids`|`queries.py`|시즌 grain 판정. 하네스로 옮기는 과정에서 구멍이 드러났다 — 10년 버킷팅은 범위 검사와 유일성 검사를 **둘 다** 통과한다|
|`expected_hand_filters`|`queries.py`|질문에서 손잡이 필터 읽어내기|
|`_CANON_RATE` / `_CANON_PLUS` / `_CANON_PLUS_SEASON`|`queries.py` → `canonical_sql.py`|재계산의 잣대|
|`is_career_grain` / `is_per_season_grain`|`queries.py`|어떤 결과가 비교 가능한가|

## 하네스에서 프로덕션으로 포팅된 검출기

하네스 검출기가 충분히 확실해지면 런타임 가드가 된다. **추측이 아니라 측정으로 결정했다:**

|검출기|포팅|근거|
|---|---|---|
|`filter_leak_flags` → `handedness_filter_leak`|2026-08-06|코퍼스 1,150롤에서 **발동한 유일한 검출기**(8회, 전부 로하스 S/R가 '왼손타자 제외'를 통과). 외국인·포지션·드래프트 검사는 0회라 손잡이만 옮겼다|
|`season_differential_flags` → `season_differential_mismatch`|2026-08-08|시즌별 결과가 프로덕션에서도 값 검사를 받게 됐다|

## pytest가 하네스를 잠근다

검출기는 LLM을 안 타는 평범한 함수라, 그 논리는 pytest가 공짜로 잠근다 — 8번 그룹의 네 파일 51개가 그것이다. 반대로 검출기가 _감시하는 대상_인 프롬프트 거동은 잠글 수 없고, 그것이 하네스를 여전히 돌려야 하는 이유다.

# 두 종류가 공유하는 설계 원칙

읽다 보면 같은 규율이 파일마다 되풀이된다. 새 테스트를 얹을 때의 기준이기도 하다.

**1. 가드-더-가드 — 테스트를 일부러 사보타주한다.** 새 가드·린트 테스트는 코드를 되돌리거나 잘못된 입력을 넣어 **실제로 실패하는지** 확인하는 짝을 가진다. `test_stat_invariants`의 세 번째 테스트(잘못된 기준선으로 15시즌 이상 걸리나), `test_counting_differential`의 `assert lint_sql(_DOUBLED) is None`(린트가 잡으면 이 픽스처는 증명력이 없다), `test_value_guard_table`의 가짜 가드 행이 전부 그것이다.

**2. 픽스처가 전제를 만족하는지도 단언한다.** `assert int(df["total_HR"].iloc[0]) == 518, "픽스처가 실제 통산 홈런 1위가 아니다"`처럼, 픽스처가 재현하려던 상황을 정말 재현했는지 먼저 확인한다. `test_retired_flag`의 "두 모집단이 모두 유의미한 크기"도 같은 종류다.

**3. 오탐과 미탐의 비용은 대칭이 아니다.** 런타임 가드의 오탐은 **정상 차트를 거부**해 방문자의 답을 뺏는다. 그래서 `test_season_differential` 같은 파일에서 가장 중요한 테스트는 _침묵을 증명하는_ 쪽이고, 프로덕션 허용오차(0.5)가 하네스(0.15) 보다 느슨하다.

**4. 표기·문구 문제는 프롬프트가 아니라 렌더 층에서 고친다.** `test_label_wording`이 그 근거를 실측으로 남겼다 — 프롬프트 4줄 수정이 완전히 무관한 결함을 0/17 → 6/19로 올렸다(Fisher p=0.014). 프롬프트는 모델의 입력이지 개발자 문서가 아니다.

**5. 결함은 로그와 하네스에서 오고, 도크스트링에 출처가 남는다.** 린트 9개 파일(린트 10종)이 전부 "제보: <질문> — <잘못된 결과>" 형태의 실제 사고에서 나왔다. 새 결함을 어디에 얹을지는 SQL_VALIDATION_PIPELINE.md의 「새 결함이 나왔을 때」 절이 다룬다.

**6. 단위 테스트는 호출부 배선을 안 지나간다.** 2026-08-07 사고(`except`가 렌더 경로를 삼킨 건)를 아무것도 못 잡은 이유가 이것이다 — 하네스는 그 코드를 설계상 우회하고, 단위 테스트는 예외를 스스로 잡았다. `test_submission_outcome`, `test_shared_chart`, `test_playground_run` 셋이 "화면 상태를 만드는 세 생산자"를 각각 그 각도에서 잠근다.

**7. 1롤은 증거가 아니다.** 생성이 비결정적이라 실패율 20%짜리 결함도 5롤에서 0번 나올 확률이 33%다. 실제로 대조군을 이력에서 고르려다 **네 번 연속 실패**했다 — 로그에 실패 이력이 있는 질문은 그 이력 때문에 이미 고쳐져 있었다. **실패 이력은 고쳐진 버그의 묘지다.** 불안정한 대상을 고르는 데는 쓸 수 없다.

**8. 검출기의 기본값은 오탐이지 미탐이 아니다.** `_floor_changes_the_result`가 그 규율을 명시적으로 적어뒀다 — 재작성이 안 먹히거나, 어느 쪽이든 에러가 나거나, 어느 쪽이든 비면 **True(=지적)를 반환**한다. 무해함을 증명하지 못하면 flag한다. 하네스 오탐은 한 번 훑어보면 끝이고, 미탐은 틀린 리더보드를 내보낸다.

**9. 발견은 하네스가, 잠금은 pytest가.** 하네스 스윕에서 나온 결함은 손으로 재현한 픽스처가 되어 `tests/`로 들어간다. 그때부터 그 결함은 LLM 콜 없이, 수십 초에, 영원히 막힌다. 린트 10종이 전부 이 경로로 생겼다. 하네스에 결함이 남아 있는 동안은 **매 실행마다 돈을 내고 같은 것을 다시 발견하는 것**이다.

# 실행 요약

```bash
uv run pytest                                  # 1,021개, 수십 초, 무료 — 소스 고칠 때마다
uv run python eval/harness.py --escalate 3     # 124질의, 실제 LLM 콜 — 프롬프트·모델 바꿀 때
```

골든 스냅샷의 `live_*` 변종은 새 시즌 데이터가 들어오는 **매년 10월에 깨지는 것이 정상**이다. diff를 검토한 뒤 재축복한다 (`FROZEN_THROUGH = 2025`는 올리지 않는다 — 올리면 frozen 변종의 보장이 사라진다):

```bash
uv run pytest tests/test_golden_snapshot.py --snapshot-update
```

하네스는 **롤 수를 먼저 승인받고** 돌린다. 비용이 롤 수에 정비례한다.
